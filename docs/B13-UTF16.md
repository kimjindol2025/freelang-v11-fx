# B-13 J_UTF16_LENGTH 원인 조사

최종 판정 전 원인 기록이다. 시작 HEAD cccfca9a354557dae0da29bf8d2d0862d6792214에서 CLEAN을 확인하고 fix/b13-utf16 가지를 만들었다. 기존 시험·기대값 3·시간제한·실행기·고정 seed는 수정하지 않았다. 임시 자료와 실제 경로·주소·소유자는 <가림>으로 표시한다.

## 비교 방법과 지점별 결과

원본 정답 파일의 SHA는 세 지점 모두 8cc56da95dfc643ae02f54eb3f878722401d8353c4dd889b21906ac0aa747867이다. browser-case 정의와 J_UTF16_LENGTH 호출을 그대로 임시 입력에 추출하고 출력 관찰용 println만 감쌌다. 임시 입력 SHA는 5e6c4c14b9e3f678092303a5aff579027144e8ad7fdca5491a7c7cb5f5b04b87다.

기존 native 경로와 seed 직후 경로를 구분했다. B9는 보존 seed→stage1 생성 C를 B9 런타임과 다시 링크했다. B10·B11은 해당 지점에서 보존한 정상 고정점 컴파일러로 생성하고 원본 지점 런타임과 링크했다. 이 native 경로는 B9·B10·B11 모두 J_UTF16_LENGTH=PASS, 종료 0이었다.

seed 직후 경로의 원인을 가리기 위해 별도 통제 비교를 했다. 공통 carrier는 보존 B12 후보 f3c88b89155dc030e827abb2bf86c4463adb38d5의 런타임이다. seed의 예전 배열 누적을 2GiB 안에서 처리하고 기존 builder C 이름·빈 구분자 호환을 제공하는 이 런타임을 세 지점에 똑같이 적용했다. 바꾼 변수는 각 지점의 self/cgc-main.fl이다. 이 표를 수정 없는 전체 FX 지점의 정식 빌드 결과로 확대하지 않는다.

| 지점 | 원본 native 경로 | 동일 carrier의 seed→stage1 경로 |
| --- | --- | --- |
| B9 85712082e647fb6278bd54e8e2e4184f8c14ed2a | 통과 | 통과, 종료 0 |
| B10 4f8a7f779de18dc9a2e11cbac9c1cd1999c26ec1 | 통과 | 통과, 종료 0 |
| B11 cccfca9a354557dae0da29bf8d2d0862d6792214 | 통과 | 실패, 종료 1 |

통제 비교에서 B9 stage1 C는 보존 B9 생성물 b4cdbc346b43708d9f218301e2c84ea49934edd3d688c1b0f5814c9680314448과 byte 동일했다. B10 stage1 C는 26a2c96ac7dc13711c5efb3c3512f657e065b578e95f8b7faa4a594fade57574다. B11 stage1 C는 489d9d20afe9bcb40e0b0caec31f07aeee1674e3ab7710e7cae6ef999742da7b로 B12 실패 경로의 생성물과 byte 동일했다.

통제 비교의 첫 실패 원문:

```text
Uncaught error (line 3): [browser-case] BROWSER_SEMANTICS_ASSERT J_UTF16_LENGTH (at line 4, col 0)
```

## 확인한 원인

원인=캐시된 UTF-16 서로게이트를 예전 fl_str_n이 이어 붙일 때 FL_TEXT 표식을 FL_STRING으로 바꿔, 이후 정상 문자 변환이 서로게이트 바이트를 손상된 UTF-8로 해석한다.

B11의 self/cgc-main.fl:37은 source를 UTF-16 문자 배열로 한 번 캐시하고 peek-at에서 get으로 읽는다. B10까지는 원본 문자열과 char-at 경로였다. seed가 출력한 1단계 C의 read_string_iter는 문자열 누적에 runtime/core.c의 fl_str_n을 직접 호출한다. 이 함수는 입력 표식을 확인하지 않고 결과를 FL_STRING으로 만든다. B9~B11 사이 이 함수는 변경되지 않았다. 정상 고정점 컴파일러가 사용하는 v11 str는 표식을 유지하고 서로게이트 쌍을 합치므로 같은 정답이 통과한다.

작은 C 진단은 기존 str-split으로 `한🙂`를 나누고 fl_str_n으로 합쳤다. 수정 전 원문:

```text
JOIN_BRANDED=0
JOIN_UTF16_LENGTH=7
JOIN_BYTES=ed 95 9c ed a0 bd ed b9 82
```

기대 길이는 원래 정답대로 3이다. 글자 길이를 단순 바이트 수로 센 문제가 아니라, 분리된 서로게이트의 표식이 사라져 각 바이트가 잘못 해석되는 문제다. compiler-bindings.h와 v11-compat.h의 B11 builder 변경도 확인했지만, 동일 carrier에서 self 소스만 바꾼 재현과 위 표식 진단이 직접적인 차이를 보였다. source 캐시 최적화를 없애지 않고 기존 v11 str 구현을 재사용하는 수정으로 확인할 예정이다.

## 실행 제한과 seed

ps 확인·공용 flock·주소 공간 2097152KiB·cgroup 2147483648바이트·swap 0·core 0 아래 순차 실행했다. 통제 비교 cgroup 최고값은 272429056바이트였다. seed는 세 지점 모두 전후 f7425bf086d99d11231ba79296e194fcc36b454379e46d44131bafb0dc74101c로 같았다. 기존 실행기와 정답은 수정하지 않았다. 원인 확인 전에는 제품 소스를 고치지 않았다.

## 수정과 좁은 재검증

runtime/core.c의 fl_str_n은 FL_TEXT 입력이 있을 때 기존 fl_v11_builtin의 str에 원래 인자들을 전달한다. 일반 legacy 문자열 경로는 유지했다. 새 문자 변환기는 만들지 않았고 B11의 문자 캐시·builder·compiler-bindings.h·v11-compat.h 최적화는 그대로다.

기존 정식 실행기를 고정 seed부터 2GiB 안에서 실행하기 위해 앞서 통제 carrier에서 사용한 호환 수정도 적용했다. runtime/collection.c의 append 전용 저장 공간은 이전 벡터의 논리 길이·요소를 보존하며, 이전 prefix에서 분기하면 복사한다. B10의 할당 실패 처리는 유지한다. runtime/aliases.c·runtime.h의 이전 builder C 이름과 빈 구분자 str_split은 기존 구현에 연결한다. runtime/http.c의 선택 환경 설정은 기존 실행기를 수정하지 않고 시험 HTTP/TLS를 loopback으로 제한하는 용도다. 이 4개 파일을 Unicode 수정과 구분해 기록한다.

수정 뒤 동일 C 진단 원문:

```text
JOIN_BRANDED=1
JOIN_UTF16_LENGTH=3
JOIN_BYTES=ed 95 9c f0 9f 99 82
```

수정 전과 byte 동일한 B11 stage1 C를 새 런타임에 링크하고, 같은 정답 입력을 다시 생성·빌드·실행한 원문은 `J_UTF16_LENGTH=PASS`, 종료 0이다. 이미 손상된 C 리터럴만 길이 3으로 취급하도록 바꾼 것이 아니라, 1단계 컴파일러에서 정답 C를 재생성해 확인했다. 기존 테스트·기대값·시간제한·실행기·seed·self 소스는 수정하지 않았다.

bootstrap 뒤 측정을 준비하던 외부 명령은 과거 입력 파일 경로가 없어 종료 1이었다. bootstrap 실행 자체는 종료 0으로 완료됐으며 반복하지 않았다. B11에 보존된 동일 SHA의 8192바이트 입력을 확인해 측정했다. 입력 SHA는 3b13bbd80fa2541f591f283ac9b38fabd5a6b34fff60c9dec4338dae2b723ac2다.

## 전체 회귀 1차: 심볼 메타데이터 누락

기존 E08 실행기와 하위 실행기를 수정 없이 실행했다. 집중 검사에서는 이전 실패 경로의 native 정답 37/37이 통과했다. 전체 실행에서도 CLI 4/4, 실제 Chrome 타이머 20/20·의미 37/37·이벤트 24/24·DOM 29/29·블록 모델 21/21, L07 221, 기존 누수 12/12, native JSON·인증·TCP·HTTP·파일·컴파일러 메모리 관문과 이전 3단계/2단계 자체 회귀가 통과했다.

이전 1단계 자체 회귀는 런타임 심볼 메타데이터의 생성 결과 비교에서 멈췄다. 추가한 실제 C 호환 함수 vec_builder·freeze_builder의 선언이 runtime/runtime.h에 있었지만, 구현에 사용하는 runtime/native-symbols.h를 갱신하지 않은 것이었다. 정답 파일의 값 비교 실패와 구분하며 전체 회귀 1차 실패로 보존한다.

```text
L08_P3_PASS=11 FAIL=0
PHASE3_SELF_EXIT=0
L08_P2_PASS=11 FAIL=0
PHASE2_SELF_EXIT=0
self_EXIT=1
NATIVE_ALL_EXIT=1
FULL_EXIT=1
ELAPSED=4011.20 MAX_RSS_KB=526224 TIME_EXIT=1
MEMORY_PEAK_BYTES=1083699200
```

후속 HTTP·취소·JSON 오류 경로·API 20개 실행은 이 실패 때문에 시작하지 않았다. 그 대기 명령은 DEPENDENCY_FULL_REGRESSION_NOT_PASSED로 종료했다.

기존 scripts/refresh-native-symbols.sh --write로 구현 메타데이터를 생성했다. 이름 집합의 추가는 freeze_builder·vec_builder 2개, 삭제는 0개다. 기존 생성기의 --check는 NATIVE_SYMBOL_METADATA=PASS, browser core 검사는 BROWSER_CORE_EMBEDDING=PASS였다. 검사기·정답·기대값·제한시간·seed·self 소스는 변경하지 않았다. 이 메타데이터를 포함한 최종 소스로 bootstrap·속도·전체 회귀를 다시 확인한다. 전체 회귀의 수정 뒤 실패 이력은 현재 1회이며, 부분 검사 통과로 전체 실패 이력을 지우지 않는다.
