# B-14 큰 파일 C 생성: 수정 전 원인 기록

시작 HEAD 419fd118f7092378efe14d064dc5c815663e9ebf의 CLEAN을 확인하고 fix/b14-big-c를 만들었다. 현재는 원인 확인 기록이며 구현·최종 판정 전이다. seed·시험·정답·실행기·시간제한·PRD 원표는 수정하지 않았다. 실제 경로·소유자·주소는 <가림>이다.

## 수정 전 입력과 측정

기존 B12 제품 source-only 사본의 실제 main.fl과 같은 모듈을 진단용 사본에서 한 번씩 펼쳤다. literal load와 실제 경로 중복을 따라 펼쳤으며 제품 원본을 고치지 않았다. 문자열·주석을 제외해 완전한 최상위 식 경계에서 1/4·1/2 prefix를 만들었다. 따라서 반쪽 입력은 정확한 byte 절반보다 다음 완전한 식까지 크다. 부분 입력은 C 생성 비용 측정용이며 제품 동작 인수로 사용하지 않는다.

기존 B12 정식 compiler를 그대로 사용했고, ps 확인·공용 flock·주소 공간 2097152KiB·cgroup 2147483648바이트·swap 0·core 0을 적용했다. TMPDIR·입력·C·계측 결과는 작업 전용 영역 <가림>에만 생성했다.

| 진단 입력 | bytes | 최상위 식 | 초 | 최대 RSS(KiB) | 종료 |
| --- | --- | --- | --- | --- | --- |
| 1/4, 식 경계 | 112998 | 242 | 6.58 | 545192 | 0 |
| 1/2, 식 경계 | 244409 | 481 | 19.83 | 1149312 | 0 |
| 전체 펼친 사본 | 450607 | 817 | 48.35 | 2074844 | 0 |

세 prefix는 구성과 식 밀도가 달라 이 표만으로 제곱 증가를 확정하지 않았다. 기존 원본 load 경로의 B12 측정은 49.70초·2073460KiB·종료 1이었다. 아래의 별도 계측 실행에서도 실제 main.fl은 마지막 generate-c:str 할당 실패로 종료했다. 펼친 진단 입력의 성공을 원래 제품 빌드 성공으로 집계하지 않았다.

## str 할당의 함수별 계측

진단용 C 계측을 작업 영역에서만 링크했다. 기존 fl_v11_context_call의 함수 이름과 str/str-join 실행 범위를 사용해 arena 요청량을 귀속했다. 기존 allocator와 함수 호출은 그대로 수행한다. 요청 바이트 합은 물리 RSS나 동시에 살아 있는 바이트가 아니다. heap scratch 요청량과도 구분한다.

1/4 입력에서 계측 출력 C는 일반 빌드 출력 C와 byte 동일했다. 계측 실행은 7.14초·544916KiB·종료 0이었다. 실제 원본 main.fl의 계측 실행은 55.14초·2071744KiB·종료 1, 다음 동일 오류였다. 계측 시간을 성능 판정용 일반 빌드와 섞지 않는다.

```text
Uncaught error (line 4596): [cgc-run] [cgc-run-positional] [generate-c] [str] text allocation failed (at line 2300, col 0)
PROFILE_OVERFLOW=0
```

| 원본 전체: str arena 요청량 순 | str 호출 | 요청 bytes | arena 할당 수 |
| --- | --- | --- | --- |
| cgc-join-lambda-loop | 1398 | 55803426 | 1398 |
| cgc-forward-loop | 557 | 22948056 | 557 |
| cgc-eval-args | 23555 | 16606562 | 70665 |

전체 str 범위의 arena 요청량 합은 155408781bytes였다. 위 세 함수는 누적 문자열을 매번 str의 첫 인자로 다시 전달한다. cgc-join-lambda-loop는 lambda·wrapper·global 선언 세 목록에서 재사용되고, cgc-forward-loop는 앞선 선언 전체를 재복사하며, cgc-eval-args는 앞선 인자 C 전체를 재복사한다. 마지막 generate-c의 str는 앞서 만들어진 큰 조각을 합치는 실패 지점이며 앞선 누적 비용과 구분한다.

원인=코드 생성의 남은 누적 문자열 경로에서 이전 prefix 전체를 반복 복사해, 큰 제품 입력의 마지막 합성에 필요한 메모리 여유가 사라진다.

DB95-26의 반복 전체 복사 수정과 같은 누적 패턴으로 대조했다. 현재 collection.c의 기존 vec-builder와 B11에서 바꾼 cgc-top-level은 조각 push 후 한 번 freeze/join하는 구현이다. 이번 세 함수에는 같은 원리가 아직 적용되지 않았다. DB95-26의 별도 실행 수치나 while 수정 기록을 이번 메모리 측정으로 재사용하지 않았다.

## 구현 전 범위

기존 지역 vec-builder에 조각을 쌓고 마지막에 str-join 한 번으로 합치는 방식으로 위 누적 경로를 바꾼다. 함수 인자·prefix·선언 순서·개행·인자 평가 순서를 유지한다. B13의 core.c FL_TEXT 처리와 문자열 reader는 변경하지 않는 방향으로 확인한다. 수정 후 같은 세 입력의 출력 C byte 비교, 실제 원본 main.fl 생성, UTF-16·전체 회귀·고정점·8192바이트·제품 인수를 별도로 확인한다.

## 구현과 첫 확인

cgc-forward-loop·cgc-join-lambda-loop·cgc-eval-args 및 같은 선언 누적 방식인 cgc-lambda-fwd-loop를 기존 지역 vec-builder/append/freeze-builder/str-join으로 바꿨다. 임시 문자열의 이전 prefix를 반복 재전달하지 않는다. 이전 시작 prefix·호출 순서·인자 평가 순서·선언 등록·개행을 유지했다. 새 이어붙이기 함수나 parser를 만들지 않았다. core.c와 v11-compat.h 및 문자열 reader는 그대로다.

기존 정식 compiler로 수정 self 소스를 생성·링크한 후보의 첫 측정은 다음과 같다. 기존 입력 세 개와 수정 전 출력 C도 그대로 보존했다.

| 입력 | 수정 전 초 | 수정 전 RSS(KiB) | 수정 후 초 | 수정 후 RSS(KiB) | 출력 C |
| --- | --- | --- | --- | --- | --- |
| 1/4, 112998bytes | 6.58 | 545192 | 6.54 | 536332 | byte 동일 |
| 1/2, 244409bytes | 19.83 | 1149312 | 19.93 | 1116184 | byte 동일 |
| 전체 펼친 사본, 450607bytes | 48.35 | 2074844 | 47.91 | 1968220 | byte 동일 |

실제 원본 load 경로의 main.fl도 이 후보로 C 생성에 성공했다.

```text
ELAPSED=48.26 MAX_RSS_KB=1966048 TIME_EXIT=0
MAIN_C_BYTES=3299307
MEMORY_PEAK_BYTES=2026999808
```

위 값은 아직 seed부터 다시 만든 최종 compiler의 측정과 구분한다. 정식 bootstrap·UTF-16·전체 회귀·제품 실제 인수는 다음 단계에서 확인한다. 한도를 올리거나 기대값을 바꾸지 않았다.
