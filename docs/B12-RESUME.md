# B-12 재개: 정식 컴파일러 빌드와 제품 인수

B12R=보류. 정식 컴파일러 빌드·전체 언어 회귀·옛 러너·추가 HTTP/취소/저장소 API는 통과했다. 블로그 본체의 C 생성은 2GiB 제한에서 마지막 문자열 합성 중 할당 실패로 중단됐다. 앱 실행 파일이 만들어지지 않아 제품 24개 실행 인수는 모두 미실행이며 PRD_PASS=0/24다.

## 출발점과 원표 보존

- FX 시작 및 검증 소스: aa6612d532c678c1412fed496000962b6520aee7. fix/b13-utf16의 CLEAN을 확인하고 feat/b12-blog-resume-2를 만들었다.
- 기존 B12의 블로그 가지: feat/b12-blog-resume, f2521082924dce224006189dad7921c7c292f9a8. 이 가지의 원장을 byte 그대로 고정했다. 원장 SHA-256은 189514da35ecf929d0b9ec2eb918c2a0965363b109b1759c045470dd005e02bb다.
- 원장의 제품 ID 24개·제목·인수 문구·선행 관계·결정은 수정하지 않았다. 원래 집계 0 passed / 13 partial / 11 pending도 원장 그대로다. 아래 결과표는 별도 검수 결과이며 끝의 원문 표에 인수 문구와 선행을 옮겼다.
- 제품 소스는 4a63271cf1c926ca7f3ff80c8877a538941719e9에서 기존 source-only 내보내기 도구로 준비했다. 기존 B12 블로그의 app/web/tests/tools와 byte 차이가 0임을 먼저 확인했다. DB 코드는 고정 46d4abf65b8c7984e65526996d26cb269634231e의 src만 포함한다. 운영 WAL·이미지·계정은 복사하지 않았다.
- 기존 구조 검증기 종료 0, CHECKPOINT_STRUCTURE=PASS, PRODUCT_TOTAL=24 PASSED=0 PARTIAL=13 PENDING=11, RELEASE_READY=false를 확인했다. 원장 SHA는 검수 뒤에도 동일했다.

## 자원·실행 조건

무거운 작업 전에 ps를 저장하고 지정한 공용 flock -o 잠금 아래 한 작업씩 실행했다. 전체 작업 cgroup은 MemoryMax=2147483648바이트, MemorySwapMax=0, core=0이었다. native 전용 명령에는 주소 공간 2097152KiB 제한도 적용했다. ASan과 Chrome은 필요한 가상 주소 공간을 허용하되 전체 물리 메모리 제한을 유지했다. 8GiB 실행은 하지 않았다.

임시파일·TMPDIR·C/ELF·생성 JS·로그·Chrome 프로필은 작업 전용 영역 <가림>에만 두었다. 지정 공용 잠금 파일을 제외하고 루트 임시 영역을 대용량 산출물 위치로 사용하지 않았다. 기존 실행기·시험·정답·시간제한·seed·PRD 원표는 변경하지 않았다. 새 수작업 JS·서버 JS·node 단계 빌드·Python은 사용하지 않았다. 기존 .fl의 Chrome용 생성 JS와 기존 시험 HTML만 사용했다.

최초 준비는 systemd PATH에서 rg를 찾지 못해 빌드 전 중단됐다. REQUIRED_TOOL=FAIL:rg, 종료 1, ELAPSED=0.00 MAX_RSS_KB=3628이었다. 이 원문을 보존하고 기존 실행기를 수정하지 않은 채 실행 환경에 PATH만 전달했다.

## 정식 빌드와 고정점

기존 verify-e10-bootstrap.sh를 수정 없이, strace 없이 실행했다. 고정 C seed를 읽기 전용 출발점으로 사용했다.

```text
STAGE0_C_BUILD=PASS
STAGE0_TO_STAGE1=PASS
STAGE1_TO_STAGE2=PASS
STAGE2_TO_STAGE3=PASS
CMP_2_3=PASS
STAGE3_TO_STAGE4=PASS
CMP_3_4=PASS
BOOTSTRAP_STATIC_AUDIT=PASS
STAGE1_SHA=489d9d20afe9bcb40e0b0caec31f07aeee1674e3ab7710e7cae6ef999742da7b
STAGE2_SHA=0dd2b662803aed1bc3392ac855a73e8c1066c07ec3bb46fee81ffa13a505f1aa
STAGE3_SHA=0dd2b662803aed1bc3392ac855a73e8c1066c07ec3bb46fee81ffa13a505f1aa
STAGE4_SHA=0dd2b662803aed1bc3392ac855a73e8c1066c07ec3bb46fee81ffa13a505f1aa

ELAPSED=141.39 MAX_RSS_KB=685608 TIME_EXIT=0
```

생성 C 고정점은 B11/B13의 0dd2b662를 유지했다. 이 stage4 C와 현재 runtime으로 다시 만든 compiler ELF SHA는 ed64ee9545b2a60fc9a46900801c51dfb640ac55673d96124abe41cf6e0c3820이다. ELF SHA는 고정점 판정에 사용하지 않았다.

기존 실행기는 STAGE0_EQ_CANONICAL=DIFFERENT도 출력했다. 허용된 현재 고정 C seed를 그대로 사용했으며 이 표기를 바꾸거나 seed를 수정·교체·재생성하지 않았다.

```text
SEED_START=f7425bf086d99d11231ba79296e194fcc36b454379e46d44131bafb0dc74101c
SEED_END=f7425bf086d99d11231ba79296e194fcc36b454379e46d44131bafb0dc74101c
SEED_DIGEST_COMPARE=PASS
```

seed 결과 파일의 전체 행을 비교할 때에는 절대/상대 파일명 표기가 달랐다. SHA 필드를 직접 비교해 위 동일성을 확인했다. 파일명 차이를 seed 변경으로 계산하지 않았다.

## 추가 언어 관문

같은 잠금을 넘겨받아 기존 HTTP·취소 Chrome 시험, JSON 실패 경로와 저장소 API를 확인했다.

```text
L01_BROWSER_HTTP_PASS=20 FAIL=0
L01_BROWSER_CANCEL_PASS=20 FAIL=0
JSON_FAILURE_CASES=18 FAIL=0
JSON_FAILURE_ASAN_UBSAN_LSAN=PASS
BROWSER_STORAGE=20/20
STORAGE_GENERATION_REPRODUCIBLE=PASS
LOOPBACK_BIND=PASS
B8_STDERR_CHECK=PASS
```

최종 추가 관문은 4/0/0이다. JSON 두 API의 실패 정답 18개는 각 100회 반복했고 ASan·UBSan·LSan과 빈 stderr 검사를 통과했다. 저장소 API는 고정 정답 SHA 70fb285b6777bf480a616bea547cf5bcb6c25fe99f55e826af1c489da61bc1f9와 실제 Chrome proof 20줄이 같았고 observer 오류는 비어 있었다. 새 compiler가 두 번 생성한 JS는 byte 동일했다. 시험 호스트도 이 실행의 compiler와 runtime으로 새로 빌드했다.

첫 저장소 Chrome은 정답 실행 전에 다음 환경 오류로 종료 134였다.

```text
FATAL:chrome/browser/process_singleton_posix.cc:313
Socket path too long: <가림>
STORAGE_CHROME_ATTEMPT1_EXIT=134
```

앞서 승인된 검수 환경 조정 범위에 따라 작업 영역 안에 짧은 Chrome TMPDIR을 두고 임시 실행 환경에서만 전달했다. 기존 실행기·Chrome 인자·정답·시간제한은 바꾸지 않았다. 완료된 HTTP·취소·JSON·생성 JS·호스트 빌드는 반복하지 않고 실패한 Chrome 저장소 단계만 새 프로필로 확인했다. 그 결과가 위 20/20이다. 최초 실패와 EXTRA_GATES_EXIT=134 이력도 보존했고, 환경 조정 후 EXTRA_GATES_EXIT=0을 따로 기록했다.

## 실제 블로그 본체의 중단 지점

앱용 autosave.fl과 기존 block-editor 빌드 도구의 브라우저 생성은 완료했다. 각각 같은 입력의 반복 생성 결과가 byte 동일했다. 이 생성 성공을 제품 화면·자동저장·미리보기 인수 통과로 집계하지 않았다.

그 뒤 운영 자료 없는 제품 소스의 main.fl을 새 compiler로 C 생성했다. 주소 공간 2097152KiB와 cgroup 2147483648바이트를 유지한 결과는 다음과 같다.

```text
Uncaught error (line 4596): [cgc-run] [cgc-run-positional] [generate-c] [str] text allocation failed (at line 2300, col 0)
Command exited with non-zero status 1
ELAPSED=49.70 MAX_RSS_KB=2073460 TIME_EXIT=1
BLOG_MAIN_C=NOT_CREATED
MEMORY_PEAK_BYTES=2131177472
```

확인한 다음 막힘은 cgc-main.fl:2300, generate-c의 마지막 str 호출이다. 이 함수는 앞에서 만든 함수 선언·전역·lambda·wrapper·함수 본문·main 본문 조각을 마지막 문자열로 합친다. 오류 프레임과 source 위치로 코드 생성의 문자열 합성 중 할당 실패를 확인했다. 앞선 조각 누적과 최종 변환 버퍼 중 어느 부분이 얼마를 차지했는지는 이번 기록으로 확정하지 않았다. O(n²) 원인이나 특정 할당 함수 하나를 확인했다고 보고하지 않는다.

실패는 1회 보존했으며 같은 앱 생성을 다시 돌리거나 2GiB 제한을 올리지 않았다. 앱 C가 생성되지 않아 링크·앱 실행 파일·제품 서버는 만들어지지 않았다. 준비했던 편집기 화면, 기존 47개, 단절·버전 보존, 서버 API 6개, 항목별 실제 화면/API 확인은 모두 미실행이다. 과거 바이너리의 통과를 이번 정식 빌드의 제품 통과로 사용하지 않았다.

1. 실제 첫 막힘은 블로그 본체 C 생성의 마지막 str 할당 실패다. 제품 24개 실행 인수 전에 이 빌드를 2GiB 안에서 완료해야 한다. 다음 별도 작업에서는 이 호출 전 누적 메모리와 요청 할당 크기를 계측해 원인을 확정하는 것이 우선이다. 이번에는 소스를 고치지 않았다.
