# B17R 누락 관문·예약 서버·메모리 재검수

B17R=보류. 빠진6종은 실제 실행했지만 전체 회귀는 출발점부터 있던 native 심볼 목록 불일치로 실패했다. PRD는2/24이며 예약 항목의 완전 인수에는 미달이다. 본체 생성은1581528KiB로 새 목표1600000KiB 이하이고, 누수12/12·API20/20·TLS3/3·생성 C 고정점은 통과했다.

## 출발점과 검사 준비

FX 출발점은1a01f3e69b7bbf63b99f0d55f6592a932e9e5646, blog1 출발점은a0d8515a91eeb1171b96457aebf9d5b745db223f다. 두 시작 작업 트리는 CLEAN이었다. 각각 fix/b17r-verify에서 작업했고 review/hermes와 기존 블로그 작업 트리는 변경하지 않았다.

검사 준비 스크립트 scripts/b17r-preflight.sh를 먼저 커밋했다. 도구 PATH, 요청 계획의 관리자/익명/native 구분, 실제 헤더 준비 함수, 결과 폴더의 작업 영역 포함 여부와 쓰기 가능 여부를 한 번에 확인한다. 각 본 검사 전에 점검을 실행한다. 관리자 인증값이 없으면 점검에서 멈추는 음성 시험도 확인했다. 실제 관리자 경로는 인증 헤더, 공개 경로는 익명 헤더를 사용한다. 합성 인증값·키·비밀번호는 기록하지 않는다.

점검 스크립트 최초 작성 이후 수정 횟수는2다. 첫 수정은 미설정 인증값의 명시적 거부, 두 번째는 실제 요청 주체/헤더 함수 확인이다. 첫 편집 명령의 구문 오류는 파일을 바꾸지 않았으므로 소스 수정 횟수에 포함하지 않았다. 점검 실패와 본 검사 실패 횟수를 구분한다.

결과 폴더를 만들기 전에 로그 리디렉션을 열었던 B17 오류를 바로잡았다. DB reader stdout의 기존 모듈 진단과 마지막 JSON 레코드도 나누어 저장한다. 원문 stdout과 종료 코드는 보존하고 JSON 객체 여부를 검사한다. 기존 정답·HTTP 예상 코드·시간 제한·시험 실행기·PRD 원표는 수정하지 않았다.

일반 산출물과 프로필은 승인 작업 영역 <가림> 안에만 생성했다. 공통 잠금과 TLS 시험 키만 사용자가 지정한 임시 영역 예외다. 무거운 검사는 ps를 기록하고 공통 flock 아래에서 한 번에 하나씩 실행한다. 각 서비스의 물리 메모리는2147483648바이트, swap은0이며 core dump를 끈다. 별도 본체·fixture 생성에는 가상 메모리 상한2097152KiB도 적용했다. 기존 sanitizer 검사는 필요한 가상 주소 예약을 유지하면서 동일한 물리 메모리 상한을 적용했다. 잠금을 강제로 풀지 않았다.

## 메모리 원인과 한 곳 수정

B17의 FX16개 변경 파일과 blog1 입력 증가를 나누어 비교했다. 같은 B17 런타임/컴파일러로 B16 본체를 생성하면58.47초·1593732KiB로, B16의1595912KiB 수준이었다. B17 본체는56.88초·1643528KiB였다. 따라서 B17 런타임16개 파일이 같은 입력의 메모리를 늘렸다는 가설은 이 비교에서 확인되지 않았다. 확장된 제품 입력이 기존 컴파일러의 이름 포함 검사 임시 할당을 더 많이 일으켰다.

재검사는 새 합성 자료로375/768/1280 각각25개 단언을 통과했다. 각 너비의 독립 reader에서 posts=28, news_total=14, news_public=1, draft=7, scheduled=7, published=7, trash=7을 확인했고 HTML 원문 cmp도 동일했다. 로컬 호스트 이외의 Host로 시험 페이지를 요청하면404였으며, 정상 제품 archive에는 시험 페이지가 포함되지 않았다. 새 손작성 JS 파일은 없다.

두 준비 오류는 각각 실패 원문 보존 후 한 번씩 해당 부분만 재검사해 통과했다. 같은 방법으로3회 실패한 관문은 없다. 제품 PRD의 다음 불충족은 별도로 한 번 확인했고 소스를 고치지 않았다.

## TLS 키 삭제와 실행 감사

각 TLS 구성마다 새 합성 키·인증서만 사용자 지정 임시 영역 <가림>에 만들었다. 일반 산출물의 실제 저장 영역은 <가림>이며, private mount/PID 격리에서 키 위치만 별도 연결했다. 키 바이트를 복사하거나 기존 서비스/SSH 키를 읽지 않았다. 각 원래 검사 종료 직후 키·인증서·CSR을 삭제했다. 세 구성의 삭제 원문은 각각 같다.

```text
POST_DELETE_LS_EXIT=0
POST_DELETE_LS_OUTPUT=EMPTY
TMP_MATERIAL_EXISTS=0
TASK_KEY_BYTES=0
KEY_FILE_COPY=0
```

종료 후 소유 TLS 임시 폴더0, 두 저장소의 키 파일명0·개인키 표지0을 확인했다. 관측한 execve 로그를 원래 감사기로 모은 원문은 NODE=0 NPM=0 NPX=0 JS=0 PYTHON=0이다. 이 JS=0은 브라우저 밖 실행 감사 범위이며 승인된 Chrome 생성 JS를 실행하지 않았다는 뜻이 아니다.
